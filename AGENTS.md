# Menetap Agent Guide

## Project overview

Menetap is a hospitality platform powered by UPSCALE. It connects:

- **Guests** who book hotels and services around their stay.
- **Partners** such as hotels, villas, serviced apartments, and property operators.
- **Vendors** providing guest services, hospitality operations, or hotel supplies.

The long-term product includes guest booking, stay extensions, partner operations, revenue and reservation services, housekeeping, photography, hospitality supplies, and vendor commerce.

The primary public domain is intended to be `menetap.com`.

## Current repository state

This folder currently contains a high-fidelity design/prototype export rather than a conventional production application.

Important files and folders include:

- `Menetap *.dc.html` — design/runtime prototype screens.
- `support.js` — generated DC runtime; do not edit manually.
- `ios-frame.jsx` — reusable iOS-style device frame component.
- `_ds/` — Aninda Wida design-system export and tokens.
- `menetap-lean-business-plan-canvas.html` — business canvas.
- `menetap-development-milestones.md` — phased development roadmap.

There is currently no `package.json`, backend, database, application build system, or Git repository in this folder. Do not assume that the prototype files are already a deployable production application.

## Product principles

- Keep the guest booking journey simple and trustworthy.
- Make availability, pricing, payment, cancellation, and payout behavior explicit.
- Treat hotel partners as customers and operating partners, not only inventory suppliers.
- Add service categories gradually; operational reliability is more important than catalog breadth.
- Use UPSCALE hospitality expertise as a meaningful operating advantage.
- Prefer transparent pricing and clear ownership of fulfillment.
- Validate major assumptions with real guests, partners, and vendors before expanding scope.

## Expected user roles

Any future application implementation should plan for role-based access for:

- Guest
- Partner/hotel operator
- Vendor
- Support agent
- Operations user
- Finance user
- Administrator/superadministrator

Do not expose partner, vendor, finance, or administrative data to guests or unrelated accounts.

## Working with the prototype files

- Preserve the existing `.dc.html` structure unless the task explicitly requests migration to another framework.
- Preserve custom DC elements such as `<x-dc>` and `<x-import>` when editing prototype pages.
- Preserve dynamic bindings such as `{{ value }}` and `onClick="{{ handler }}"` unless intentionally replacing the runtime.
- Reuse design-system tokens from `_ds/.../tokens/` instead of inventing unrelated colors, typography, spacing, or motion values.
- Follow the existing visual language: light violet background, electric violet primary accent, cyan secondary accent, Plus Jakarta Sans for display text, and JetBrains Mono for body/UI text.
- Do not edit `support.js` directly. It is generated by the DC runtime.
- External CDN dependencies may prevent offline rendering. Call this out when testing or preparing a production migration.

### Brand and visual direction

Menetap uses the light adaptation of the UPSCALE visual language:

- Light violet page background: `#F7F6FF`.
- White surfaces and cards: `#FFFFFF`.
- Deep violet-charcoal ink: `#0C0A1E`.
- Electric violet primary accent: approximately `#7229FF` in the Menetap screens and `--color-violet-500` (`#7C5CFC`) in the shared token scale.
- Electric cyan secondary accent: `--color-cyan-500` (`#00D4FF`) in the shared token scale.
- Violet-tinted borders: `#E5E2F5`.

Prefer design tokens over hard-coded values. If a screen uses a legacy prototype value, preserve it unless the task includes a design-system cleanup.

### Typography

- **Display:** Plus Jakarta Sans for headings, hero copy, large numbers, and brand lockups.
- **Body and UI:** JetBrains Mono for body copy, navigation, labels, forms, data, and technical content.
- Use sentence case for headings.
- Use concise, verb-first CTAs such as “Search stays”, “Add transfer”, “Save changes”, and “View booking”.
- Keep display line-height tight and body line-height generous for readability.

### Menetap type hierarchy

Use this hierarchy across the React implementation unless a DC reference screen explicitly requires a documented exception:

| Role | Size | Weight | Typical use |
|---|---:|---:|---|
| Display / hero | 48px desktop, responsive down to 36px | 800 | Homepage hero headline |
| Page heading | 40–44px | 800 | Major page titles |
| Section heading | 24px | 800 | Homepage and dashboard sections |
| Card heading | 18px | 700–800 | Property, room, and service names |
| Body | 14px | 400–500 | Descriptions, footer copy, primary content |
| Navigation / controls | 14px | 500–700 | Topbar links and primary controls |
| Labels / eyebrows | 12px | 600–700 | Form labels, section eyebrows, metadata headings |
| Supporting metadata | 11px | 400–600 | Prices, hints, badges, secondary context |

Use Plus Jakarta Sans for display and headings, and JetBrains Mono for body/UI text. Do not reduce body or footer copy below 14px without a specific component-level reason.
- Fonts are currently loaded through the design-system font token file and may use a remote Google Fonts import.

### Layout and spacing

- Use the 4px spacing base unit.
- Common scale: 4, 8, 12, 16, 24, 32, 48, 64, 96, and 128px.
- Use a 24px mobile gutter and approximately 48px desktop gutter.
- Use a maximum content width of approximately 1200px unless the screen requires a different layout.
- Maintain generous vertical rhythm between major sections.
- Prefer responsive layouts that work on mobile first, then expand for desktop.

### Surfaces, borders, and shadows

- Default cards use a white surface, a 1px violet-tinted border, and an approximately 8px radius.
- Use subtle violet-tinted shadows rather than neutral gray shadows.
- Use 4px radii for small controls, 8px for cards and panels, and pill radii only for tags, badges, toggles, and compact actions.
- Avoid excessive glass effects. Backdrop blur is appropriate for sticky navigation or floating controls, not for every card.
- Avoid full-bleed gradients and textured backgrounds. Keep the page grounded and calm.

### Components

Reuse the design-system component patterns where available:

- `Button` — primary, secondary, ghost, and outline actions in small, medium, and large sizes.
- `Card` — default, elevated, and outlined surfaces.
- `Badge` — status labels such as confirmed, pending, success, warning, or error.
- `Input` — labeled fields with hint and error states.
- `Tag` — compact category labels.
- `Stat` — metrics with labels and deltas, useful for partner and admin dashboards.

When adding a new reusable pattern, first check whether it belongs in the shared component system rather than duplicating inline markup across pages.

### Iconography

- Use Lucide icons, loaded by the existing prototype CDN integration where appropriate.
- Use a consistent stroke-based style; do not mix filled icon families without a deliberate reason.
- Typical sizes: 16px for inline labels, 20px for buttons, and 24px for standalone controls.
- Icons should support the label, not replace important text.
- Provide accessible labels for icon-only controls.

### Motion and interaction

- Use the standard easing curve `cubic-bezier(0.22, 1, 0.36, 1)`.
- Use approximately 150ms for micro-interactions, 250ms for standard transitions, and 400ms for entrances.
- Use small lifts such as `translateY(-1px)` for card hover states.
- Use subtle color and shadow changes for buttons and links.
- Use approximately `scale(0.97)` for press feedback where appropriate.
- Avoid bouncy, infinite, or decorative animation that distracts from booking and operations.
- Respect `prefers-reduced-motion` in production UI.

### Imagery and content

- Prefer warm-neutral, genuine hospitality photography over generic stock imagery.
- Do not introduce AI-generated imagery into the core brand system unless explicitly approved.
- Keep imagery slightly desaturated and consistent across a property or service category.
- Use descriptive image alternative text, especially for hotel, room, and amenity images.
- Keep copy direct, warm, transparent, and practical. Avoid inflated claims and fake urgency.

### Accessibility and trust

- Maintain readable contrast for text, links, controls, and status colors.
- Do not communicate booking, payment, or reservation state with color alone.
- Keep focus states visible and keyboard navigation functional.
- Use semantic headings, labels, buttons, and form controls.
- Make price breakdowns, cancellation terms, taxes, fees, and service conditions easy to find.
- Clearly distinguish confirmed, pending, failed, cancelled, refunded, and action-required states.

## Development priorities

When implementing the product, use this order unless the user directs otherwise:

1. Product validation and launch-market definition.
2. Authentication, roles, data model, and environment setup.
3. Guest hotel search, property detail, room selection, checkout, payment, and confirmation.
4. Partner property, inventory, rate, and reservation management.
5. A small number of operationally reliable stay extensions.
6. UPSCALE-powered partner services.
7. Vendor onboarding, fulfillment, quality, and payouts.
8. Production hardening, monitoring, deployment, and post-launch optimization.

Avoid building the full vendor marketplace before the core booking and fulfillment loop is reliable.

## Quality requirements

For any production-oriented change:

- Validate loading, empty, error, success, and permission-denied states.
- Test mobile and desktop layouts where the change affects UI.
- Test date, timezone, currency, availability, cancellation, payment, and refund edge cases when relevant.
- Keep payment, reservation, and payout state transitions auditable.
- Avoid logging passwords, payment details, access tokens, or unnecessary personal data.
- Add or update documentation when behavior, setup, or deployment changes.
- Run the most relevant available checks before reporting completion.

## Security and data handling

- Never commit secrets, production credentials, API keys, or private customer data.
- Validate and authorize every server-side operation; do not rely only on client-side role checks.
- Use least-privilege access for admin, partner, vendor, finance, and support operations.
- Keep an audit trail for changes to bookings, prices, inventory, refunds, payouts, and user access.
- Treat guest identity, contact, payment, booking, and location information as sensitive.
- Use approved payment-provider flows; do not store raw card data.

## Deployment expectations

Before deploying to `menetap.com`:

- Confirm production environment variables and secrets are configured securely.
- Confirm DNS, HTTPS, email delivery, payment webhooks, storage, backups, and monitoring.
- Run production smoke tests for guest booking, partner reservation access, payment status, confirmation email, cancellation, and support workflows.
- Confirm rollback and incident-response procedures.
- Do not deploy unverified hotel inventory, rates, vendor services, or legal documents.

## Change discipline

- Inspect existing files and preserve unrelated user work before editing.
- Prefer small, focused changes.
- Use the repository's existing conventions when an application framework is introduced.
- Avoid destructive commands and broad rewrites without explicit approval.
- When a requirement is ambiguous, make the smallest reversible assumption and document it.
- Report what changed, what was verified, and any remaining risks.

## Communication style

Use clear, direct language. Lead with the outcome. When discussing product decisions, distinguish between:

- Validated facts
- Current assumptions
- Recommendations
- Open decisions requiring stakeholder input
